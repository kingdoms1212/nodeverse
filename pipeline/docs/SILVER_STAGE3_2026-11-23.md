# 3단계 Silver 최적화 실험 — 2026-11-23

## 범위와 운영 상태

Silver MERGE 그룹별 경계 계산을 묶고 그룹 수를 제한하며, 원격 outbox를 일정 크기의 묶음으로 나누는 실험 코드입니다. `SILVER_OPTIMIZATION_ENABLED=0`이 기본값이며 기존 운영의 168시간 중복 제거 설정을 바꾸지 않습니다. `1`은 격리 시험에서만 사용하세요. 실제 운영 프로세스에는 배포하지 않았습니다.

## 성능 결과의 범위

`evidence/SILVER_STAGE3_2026-11-23.json`은 격리된 Spark 3.5.3·Delta 3.2.1에서 2만/20만 행과 301개 배치를 비교한 각 1회 결과입니다. 기존 그룹 방식과 실험 방식의 전체 시간은 2만 행에서 14.537초→12.665초, 20만 행에서 12.599초→10.125초였습니다. 한 번씩 측정한 수치이므로 운영상 개선을 입증하지 않습니다. 이벤트 로그의 task input은 전체 작업의 입력 지표이고 MERGE가 읽은 실제 파일 바이트와 동일하다고 단정할 수 없습니다. UUIDv4/v7 혼합 및 중복 재실행을 포함했으나 실제 운영 데이터와 부하를 대표하지 않습니다.

별도 Python 메모리 프로브는 10만 행을 모의 sink로 보낼 때 할당 피크 약 79.6MB→0.8MB를 기록했습니다. 프로세스 RSS, 실제 MongoDB 및 Spark `toLocalIterator`의 파티션 메모리는 측정하지 않았으므로 전체 메모리 상한으로 해석하지 마세요.

## 복구 확인

- 격리 MongoDB에서 3건 저장 후 실패를 주입하고 전체 10건을 두 번 재전송: 10건 고유, 기존 항목 유지, ID 충돌 1건 기록.
- 격리 Spark·Delta·MongoDB에서 301건 배치의 MERGE 완료 후 outbox 100건 저장 시 실패를 주입하고 같은 배치를 명시적으로 재실행: Silver 1,251행과 outbox 301건, Silver 중복 0건. 이는 체크포인트 자동 재시작이 아닌 직접 재실행 시험입니다.
- Python 묶음 재시도 및 기본 비활성화 검사 통과. 최초 복구 실험의 기대 건수는 작은 시험 데이터와 맞지 않아 수정했고, 수정 후 재시험했습니다.

재현: 새 빈 디렉터리를 `SILVER_RECOVERY_OUTPUT`으로 지정한 뒤 `docker compose -f compose.silver-recovery.yaml up --abort-on-container-exit --exit-code-from experiment`를 실행합니다. 로컬 Spark 이미지와 읽기 전용 Ivy 볼륨이 필요하며, MongoDB는 외부와 단절된 별도 컨테이너입니다. 기존 시험 디렉터리나 DB는 덮어쓰지 않습니다.

## 남은 검증

실제 스트리밍 체크포인트 재시작, 원격 MySQL·MongoDB 및 Gold/대시보드 전체 경로의 부분 성공·중복·순서 복구, 다양한 배치와 v4/v7 비율에 대한 반복 측정, 100만 행 규모 및 실제 스캔 지표를 추가 확인해야 합니다. 현재 결과만으로 운영 활성화나 성능 개선을 확정하지 않습니다.
