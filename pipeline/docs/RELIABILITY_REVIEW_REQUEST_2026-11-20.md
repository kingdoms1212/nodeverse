# NODEVERSE 파이프라인 신뢰성 보완 요청

2026년 11월 20일 작업본을 검토한 결과입니다. 게임에서 나온 학습 기록이 Kafka, Spark Structured Streaming, Delta Lake를 거쳐 서버까지 이어지는 기존 프로젝트 목표를 기준으로 보완해 주세요. 수정 우선순위는 **이벤트 선점 경쟁 → 다음 순번 복구 → 잘못된 이벤트의 무한 대기**입니다.

현재 작업본의 단위 테스트는 60개 통과, 1개 건너뜀입니다. 건너뛴 항목은 PySpark가 필요한 Silver `MERGE` 조건 테스트입니다. 아래의 ‘재현’은 메모리 테스트 DB에서 실패나 실행 순서를 주입한 결과입니다. 운영 장애를 재현한 기록과 종단 시험은 각각 별도로 확인합니다.

## 원래 프로젝트 목표와 보완 범위

| 원래 목표 | 보완 후에도 확인할 구현과 증거 | 목표에 미치는 영향 |
|---|---|---|
| **실제 게임 → 서버 학습 기록** | 최신 배포 EXE에서 문제 시작, 시도, 오답, 힌트, 성공을 발생시킵니다. 같은 `event_id`를 Kafka·Bronze·Silver·원격 DB에서 추적하고 회원 화면을 확인합니다. 종료·재실행과 로그아웃·계정 전환도 포함합니다. | 게임 큐와 원격 복구 보완은 서버까지 기록이 이어지는 목표를 강화합니다. |
| **Kafka 수집과 토픽·파티션·복제 설계** | 학습 토픽의 `session_id` 키, 현재 토픽·파티션, 복제 계수 3, 최소 ISR 2, 7일 보관, Kafka 접수 후 `202` 응답을 확인합니다. | 헬스체크 보완은 기동과 장애 감지에 해당합니다. 토픽과 수집 계약 변경은 별도 설계 검토 사항입니다. |
| **Spark 스키마·워터마크·시간 창 집계** | 명시 스키마와 Silver 중복 제거 워터마크, Gold의 1분 Tumbling Window와 1분씩 이동하는 5분 Sliding Window를 실제 데이터로 확인합니다. | 골드 지표 재게시와 화면 보완은 기존 Spark 계산 결과의 전달을 강화합니다. 시간 창, 오답률 정의 또는 비교 계산을 바꾸는 일은 별도 기능 변경입니다. |
| **Exactly-once 의미와 체크포인트 복구** | 기존 체크포인트로 재시작하고 동일 원문을 재전송합니다. Silver의 고유 이벤트 수와 Gold 집계값을 대조하고, 원격 적재는 동일 이벤트의 최종 결과로 수렴하는지 확인합니다. | 작업 선점과 재실행 보완은 단계별 중복 방지와 복구를 강화합니다. Delta·MongoDB·MySQL 간 저장은 단계별로 검증합니다. |
| **Delta Lake Bronze → Silver `MERGE` 증분 적재 및 `OPTIMIZE ZORDER`** | Bronze의 원본 append, Silver의 `event_id` 기준 insert-only `MERGE`, Gold 집계 테이블을 확인합니다. Delta 테이블의 스냅샷에서 행을 대조하고, `OPTIMIZE ZORDER` 전후의 행 수·파일 수·스캔량·실행 시간을 같은 조건에서 비교합니다. | 이번 보완의 핵심은 Delta 이후의 복구와 게시입니다. **Bronze·Silver·Gold를 축소하거나 Silver `MERGE`를 단순 append로 바꾸는 것은 원래 요구사항에 영향을 줍니다.** 이를 변경하려면 별도 설계 검토가 필요합니다. |
| **지연과 처리량 튜닝** | 같은 입력률·이벤트 수·초기 테이블 크기에서 Kafka 접수, Silver `MERGE`, Gold 지표 반영, 상세 기록 적재 완료를 각각 측정합니다. 피크 CPU와 outbox 적체도 함께 비교합니다. | 아카이브 조회 절감과 선점 방식 변경은 정확성과 성능을 함께 확인해야 합니다. 처리량 수치만으로 단계를 완료했다고 판단하지 않습니다. |

검토 결과, 아래 **P1의 원격 적재 보완은 원래 다섯 가지 기술 목표 범위 안**입니다. **P2의 게임·대시보드·인프라 항목은 실제 게임부터 서버까지 검증하는 데 필요한 보완 또는 시험**이며, Kafka·Spark·Delta 구현 증거는 위 표의 항목으로 계속 확인합니다. Silver `MERGE` 날짜 범위·워터마크·체크포인트 경로 변경은 이번 수정과 별도의 검토로 다뤄 주세요.

## P1 수정 요청

| 순서 | 시나리오와 관찰 | 요청 및 검증 기준 |
|---|---|---|
| 1 | **선점 중 운영자 `park`와 경쟁.** 조회 뒤 DB에서 행이 `parked`로 바뀌었는데 `claim_batch()`가 메모리에서는 `processing`으로 반환했습니다. 재현했습니다. [배치 선점](../remote/worker.py#L65) · [완료 상태 기록](../remote/worker.py#L117) | 실제 선점에 성공한 행만 처리하고 완료·재시도 갱신을 선점 소유권과 연결해 주세요. 선점 전에 `park`가 성공하면 해당 행의 투영이 실행되지 않아야 합니다. 작업자 교체 뒤 이전 작업자가 결과를 덮어쓰지 않는지도 확인해 주세요. |
| 2 | **다음 순번을 깨우기 전에 쓰기 실패.** 순번 커서는 전진했지만 다음 이벤트는 `parked`로 남았습니다. 앞선 이벤트를 재실행해도 이미 처리한 결과만 반환했습니다. 재현했습니다. [영수증·다음 순번 처리](../remote/projection.py#L96) · [재실행 분기](../remote/projection.py#L132) | 정상 처리와 재실행 모두 다음 순번을 안전하게 깨울 수 있도록 공통 처리 경로를 사용해 주세요. 커서 갱신 직후 실패를 주입하고, 앞 이벤트 중복 없이 뒤 이벤트가 자동으로 처리되는지 확인해 주세요. |
| 3 | **`attempt_id`가 누락된 이벤트의 무한 대기.** 대기를 시작한 지 2일, 300회 시도한 행도 `waiting_context`에 남고 세션 커서가 전진하지 않았습니다. 재현했습니다. [시도 투영](../remote/projection.py#L181) · [대기 기한](../remote/worker.py#L184) | 수정 불가능한 이벤트와 아직 도착할 수 있는 선행 이벤트를 구분해 주세요. 실제로 도착한 연속 순번의 불완전한 이벤트는 원본과 사유를 보존하며 격리하는 경로를 검토해 주세요. 실제 누락된 순번은 그대로 대기해야 합니다. `attempts_still_open` 등 다른 잠재적 무기한 대기 사유에도 복구 또는 종료 조건이 있는지 확인해 주세요. |
| 4 | **재시도 한도에 도달한 이벤트를 수동으로 재처리.** `requeue` 후 일시 오류가 한 번 나면 누적 시도 횟수 21로 다시 `parked`가 됐습니다. 재현했습니다. [수동 재처리](../remote/requeue.py#L55) | 수동 재처리 때 사용할 재시도 예산을 명확히 정의해 주세요. 누적 시도 이력은 보존하고, 재처리 직후 일시 실패 후 정상 복구되는지 테스트해 주세요. |
| 5 | **원격 DB 교체·백업 복원 뒤 아카이브 누락.** 기존 성공 시각이 남은 런타임 이벤트는 새 DB에 원본 0건인데도 `stored`가 됐습니다. 재현했습니다. [아카이브 확인](../remote/worker.py#L124) | 평상시의 중복 조회 절감은 유지하면서 원격 복구·교체 때 아카이브를 재검증하고 다시 채울 수 있게 해 주세요. 원격이 비어 있는 경우 원본 기록이 실제로 생긴 뒤 상태가 완료되는지 테스트해 주세요. |
| 6 | **Gold 저장 후 MongoDB 게시 실패.** Gold 호출부가 MongoDB upsert의 최종 실패 반환값을 사용하지 않습니다. 코드에서 확인했습니다. [Gold 게시](../spark/gold.py#L40) · [저장 재시도](../spark/sinks.py#L28) | 실패한 시간 창을 추적하고 MongoDB 복구 뒤 **Gold Delta 결과를 다시 게시**할 수 있게 해 주세요. 장애가 난 창에 새 입력이 없어도 복구되고, 같은 창을 반복 게시해도 값이 부풀지 않아야 합니다. |

## P2 시나리오와 검증

| 시나리오 | 확인할 내용 |
|---|---|
| **다수 사용자 동시 전송** | 서로 다른 세션과 한 세션의 역순 입력을 섞습니다. 회원·세션이 섞이지 않고 순번이 유지되며, 한 세션의 대기가 다른 세션의 처리를 막는지 측정합니다. 이전 시험은 수집 초당 약 170~185건, 상세 원격 적재 약 60~90건이었습니다. [부하 기록](../../docs/changes/2026-11-20_pipeline.md#L103) |
| **같은 배치에 동일 ID와 다른 본문** | 같은 ID·같은 본문과 같은 ID·다른 본문을 각각 보내고, Silver에 남는 원문과 감사 쿼리의 `id_conflict` 판정이 일치하는지 확인합니다. 선택 규칙을 바꾸게 되면 상태 저장소와 체크포인트 영향도 검토합니다. [충돌 검토](DELTA_REQUIREMENTS_REVIEW_2026-11-20.md#L86) |
| **게임 디스크 오류와 강제 종료** | 큐 파일 쓰기 실패를 감지하고, 임시 파일에서 최종 파일로 안전하게 게시하는 방식을 검토합니다. 쓰기 도중 종료, 디스크 부족, 깨진 JSON 복구를 확인합니다. 실패한 파일은 원인 추적이 가능해야 합니다. [게임 디스크 큐](../../game/scripts/network_manager.gd#L628) |
| **로그아웃과 계정 전환** | A 계정 이벤트가 미전송인 상태에서 로그아웃하고 B로 로그인한 뒤 네트워크를 복구합니다. 재실행을 포함해 기존 이벤트는 원래 회원에 귀속되고 B는 독립 세션을 사용하는지 확인합니다. [로그아웃 처리](../../game/scripts/nodeverse_world.gd#L2465) |
| **의존 서비스 지연 기동·응답 정지** | 최신 Kafka·MongoDB 검사 방식에서 포트 연결은 되지만 실제 API가 응답하지 않는 경우를 확인합니다. Kafka 토픽 초기화의 재시도, MongoDB 준비 확정, Spark 쿼리 복구를 검증합니다. [Compose 생성기](../build_compose.py#L42) |
| **동시 적재 중 대시보드 조회** | 일부 참조가 아직 읽히지 않은 상태에서 500 오류가 발생하지 않고, 적재 완료 후 동일 조회에서 행동 수·시도 수·실패율이 수렴하는지 확인합니다. [분석 조회](../../server/telemetry/mongo.py#L142) |

## 제출할 검증 결과

- P1 변경마다 실패 재현과 수정 후 결과를 남겨 주세요. 메모리 테스트, 실제 Spark·MongoDB 연동 시험, 최신 EXE 종단 시험의 수행 여부를 각각 표시해 주세요.
- Delta 기능의 증거를 따로 남겨 주세요. 동일 ID 재전송 시 **Bronze 원본의 수신 이력**, **Silver 고유 행 1건**, **Gold 집계값 불변**을 해당 테이블에서 직접 확인합니다. 기존 체크포인트 복구와 `OPTIMIZE ZORDER` 전후 비교 결과도 포함합니다.
- Windows 로컬 서비스나 팀 서버의 기존 데이터에 영향을 주지 않도록 장애·복구 비교는 별도 시험 스택과 볼륨에서 수행해 주세요. 이번 수정에 포함하는 변경과 별도 설계 검토가 필요한 변경을 보고서에 명시해 주세요.
