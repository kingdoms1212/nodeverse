# NODEVERSE 파이프라인 CPU 최적화 요청

2026년 11월 20일 로컬 WSL2 환경에서 확인한 CPU 피크를 줄여 주세요. Kafka와 MongoDB의 기동·장애 감지, 실시간 지표의 시간 창, 이벤트의 중복 방지와 세션 순서 보장을 유지해 주세요.

## 변경 전 기준

22:38:31~22:43:39 KST에 컨테이너별 CPU 표본을 300개 수집했습니다. CPU 100%는 논리 코어 하나 기준입니다. 측정 중 확인한 Spark Bronze 진행 표본의 배치 ID는 같았고 입력 행은 0건이었습니다. Spark 쿼리 재시작은 기록되지 않았습니다. 가장 높은 순간에 측정 대상 서비스가 합계 약 5.9코어를 사용했습니다.

| 구성 | CPU 중앙값 | 순간 최대 | 관측 근거 |
|---|---:|---:|---|
| Spark | 11.2% | 353.3% | 상위 피크 시각에 실시간 요약, 버전 집계와 Delta `MERGE`, Silver 감사 배치가 실행됨 |
| Kafka 브로커 3대 | 각 2.1~2.7% | 각 150~154% | 브로커별 상위 8개 피크가 모두 `kafka-topics.sh --list` 헬스체크와 겹침 |
| MongoDB | 2.0% | 47.0% | 상위 8개 피크가 모두 `mongosh` 헬스체크와 겹침 |
| 원격 적재 작업자 | 0.8% | 8.4% | 유휴 측정에서 상대적으로 낮은 CPU 사용량 |

이전 더미 이벤트 시험에서는 Silver 학습 배치당 약 5초가 `MERGE`에 쓰였습니다. MongoDB outbox는 약 13.5만 건이었고 상태별 건수 집계의 실행 계획에서 전체 컬렉션 스캔(`COLLSCAN`)을 확인했습니다.

## 우선 수정

### 1. Kafka·MongoDB 헬스체크 경량화

- Kafka 브로커마다 약 10초에 한 번 JVM 기반 `kafka-topics.sh --list`를 실행하는 비용을 줄여 주세요. 경량화한 헬스체크가 연결 가능 여부만 확인한다면, `topic-init`이 실제 Kafka API 준비 상태를 확인하고 재시도하는 경로도 함께 검토해 주세요. [Compose 생성기 Kafka 설정](../build_compose.py#L23) · [초기 토픽 생성](../build_compose.py#L45)
- MongoDB의 `mongosh` 실행 비용을 줄일 수 있는 검사 방식이나 간격을 비교해 주세요. Spark·원격 작업자가 의존하는 MongoDB 준비 상태와 장애 감지를 검증해 주세요. [Compose 생성기 MongoDB 설정](../build_compose.py#L64)
- 설정을 수정하면 `build_compose.py`로 `compose.json`을 다시 생성해 주세요. [Compose 설정](../compose.json)

### 2. Spark 주기 집계 비용 절감

- `rt_summary`는 기존 파티션 조건을 유지하면서 집계 전에 `received_at` 최근 5분 필터를 적용해 읽는 데이터를 줄이는 방안을 검토해 주세요. 최근 1분 이벤트 건수와 최근 5분 활성 세션 수는 기존 결과와 대조해 주세요. [실시간 요약](../spark/periodic.py#L20)
- 버전별 설치 수와 비율이 같을 때 매분 실행되는 Delta `MERGE`와 MongoDB 재쓰기를 줄일 수 있는지 검토해 주세요. 새 입력이 없어도 24시간 창에서 만료된 플레이어와 버전이 빠져야 합니다. 실시간 요약의 갱신 시각과 대시보드 지연 표시도 함께 확인해 주세요. [버전 집계](../spark/periodic.py#L33) · [대시보드 갱신 상태](../../server/telemetry/live.py#L62)
- 시간대가 겹친 Silver 감사 배치도 변경 전후 Spark 작업 이력에서 비교해 주세요. 요약과 버전 집계 비용을 줄인 뒤에도 큰 피크가 남으면 감사 배치의 실행 시간과 처리 지연을 확인해 주세요. [Silver 감사 쿼리](../spark/silver.py#L159)

### 3. 원격 적재 상태 집계 경량화

- 10초마다 outbox 전체를 집계하는 경로에서 인덱스만 읽는 방식이나 상태와 사유 집계의 갱신 주기를 다르게 두는 방식을 비교해 주세요. 실행 계획의 `totalDocsExamined`, `totalKeysExamined`, 실행 시간과 대시보드 갱신 지연을 변경 전후에 기록해 주세요. 상태·사유별 집계값은 기존 `status` 명령과 대조해 주세요. [상태 집계](../remote/requeue.py#L31) · [상태 발행](../remote/worker.py#L248)

## 부하 시험에서 후속 검토

- **Silver `MERGE`**. UUIDv4와 UUIDv7이 섞인 기존 테이블과 UUIDv7만 포함한 시험 테이블을 비교해 파일 스캔량과 `MERGE` 시간을 측정해 주세요. 날짜 범위나 쓰기 방식을 바꾸는 경우 늦은 재전송과 체크포인트 복구에서도 중복 행이 생기지 않는지 검증해 주세요. [Silver 쓰기](../spark/silver.py#L72)
- **원격 적재의 중복 아카이브 조회**. `process_job()`과 `Projector.project()` 양쪽에서 `archive()`를 호출하는 경로를 정리할 수 있는지 검토해 주세요. 회원 매핑이 없는 이벤트의 원본 아카이브, 같은 이벤트의 재실행, 다른 페이로드로 같은 ID를 보낸 경우의 충돌 처리, 세션 내 순서 보장을 검증해 주세요. [작업자](../remote/worker.py#L124) · [투영](../remote/projection.py#L117)

## 완료 기준

- 동일한 로컬 스택에서 5분 유휴 측정을 반복하고, 구성별 CPU 중앙값·95백분위·최댓값과 코어 하나 이상을 사용한 표본 수를 비교합니다. 헬스체크·Spark 작업 시각과 Bronze 입력량도 함께 기록합니다.
- 변경 전후 동일한 입력률과 이벤트 수로 부하 시험을 수행합니다. Spark 배치 시간, 대시보드 반영 지연, 원격 적재 완료까지 걸린 시간과 종료 시점의 outbox 대기 건수를 비교합니다.
- 브로커 및 MongoDB 지연 기동과 일시 장애를 재현하고, 지표의 시간 창 만료와 이벤트 재처리의 중복 방지를 검증합니다. 변경별로 측정 결과와 남은 병목을 남깁니다.
