# 7차 보완: 늦게 도착한 데이터 처리 (2026-11-21)

배경: 오프라인 큐, 수집 서버 장애 복구, 필수 업데이트 대기 때문에 며칠 전 플레이 기록이 오늘 처음 도착할 수 있습니다(게임이 6일 지난 기록은 만료). 원칙은 다음 세 가지입니다.

- **저장:** 어떤 데이터도 버리지 않습니다.
- **실시간 화면:** 도착 기준으로 모두 세고, 늦은 것을 따로 보여 줍니다.
- **날짜별 학습 통계:** 실제 플레이 날짜 기준으로 셉니다. 이것은 분석 화면이 맡습니다. 원격 적재가 세션·시도·이벤트에 플레이 시각을 그대로 넣으므로 이미 그렇게 동작합니다.

**시간축 원칙:** 실시간 화면(Gold, rt_*)은 도착 시각, 분석 화면(전체 현황·게임 분석·플레이어)은 플레이 시각입니다. 실시간 화면 설명 문구에 이 원칙을 적었습니다.

처음에는 플레이 날짜 기준 일별 Gold 테이블(`gold.daily_play`, `rt_daily`)과 화면 카드도 만들어 시험했습니다(사흘 전 기록 602건이 11-17에 집계됨, 재계산 2.8~4.6초). 그런데 같은 지표가 두 시간축의 Gold에서 다른 값으로 나와 헷갈릴 수 있어서, 논의 후 빼기로 했습니다. 시험한 테이블과 컬렉션도 지웠습니다.

## 1. 정의 (`pipeline/common/lateness.py`)

| 항목 | 규칙 |
|---|---|
| 늦은 이벤트 | `|received_at − occurred_at| > 300초` (Silver가 event_time을 수신 시각으로 바꾸는 기준과 같음) |
| 플레이 시각 | `occurred_at`을 `[received_at − 6일, received_at]`로 자름 (기기 시계가 미래이거나 너무 오래된 경우 방지) |
| ID 생성일 | UUIDv7 앞 48비트(ms)의 UTC 날짜, v4 등은 없음 |

### 3-1. 실패 급증 경고 (정시 이벤트만)

늦은 기록이 들어온 23:40~23:45 구간의 집계를 비교했습니다.
- 1분 미니게임 집계(모든 이벤트): 시도 366건
- 같은 시작 시각의 5분 경고 창(정시 이벤트만): 시도 282건

차이 84건은 늦게 도착한 기록의 시도 수(84)와 정확히 같습니다. 늦은 기록은 일반 집계에는 들어가고 경고 판정에서만 빠졌습니다.

### 3-2. 시험 중 생긴 데이터 오류 5건 (시험 도구 문제)

원격 적재에서 `blocked` 5건이 생겼습니다(dummy-0030 한 세션). 원인은 시험 도구입니다. 사흘 전 기록 파일과 현재 트래픽을 같은 초에 만들어 run_id가 같아졌고, 그 결과 두 갈래에 같은 session_id가 생겼습니다. 같은 세션·같은 순번에 다른 이벤트가 들어와 `id_content_conflict`(4건)와 `event_before_problem_start`(1건)로 막혔습니다. 실제 게임은 session_id를 무작위 UUID로 만들므로 이런 충돌이 생기지 않습니다. 파이프라인은 덮어쓰지 않고 막아야 하는 경우를 막은 것입니다.

## 4. 대량 수집 때의 고려

| 지점 | 영향 | 대응 |
|---|---|---|
| 수집기·Kafka·Bronze | append만, 순간 유입량 문제 | maxOffsetsPerTrigger로 배치 크기 제한 (기존) |
| Silver MERGE | 늦은 ID가 범위를 넓히던 문제 | ID 생성일별 분리 (이번) |
| 플레이 날짜 집계 | 스트리밍으로 하면 6일 치 창 상태가 필요 | 스트리밍으로 만들지 않음. 분석 화면이 원격 적재 데이터(플레이 시각)로 담당 |
| 실시간 지표 | 늦은 이벤트 몰림 = 순간 급증처럼 보임 | 총계에 포함하되 늦게 도착 건수 표시, 경고는 정시 이벤트만 |
| 원격 적재 | 세션 순서 처리라 다른 세션을 막지 않음(5차 시험) | 처리량(초당 50~90건)이 대량 유입 시 병목으로 남음 |
