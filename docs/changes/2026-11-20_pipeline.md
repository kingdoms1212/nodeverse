## 3. 원격 적재 작업자 (`remote/worker.py`, `sql.py`, `metrics.py`)

**이전:** 한 번에 1건, 이벤트마다 MySQL 새 연결 + `GET_LOCK`, 5초마다 rt_* 전체 복사를 같은 루프에서.

**지금:**
1. `claim_batch(local, REMOTE_BATCH=200)`: due 상태 행을 한 번에 가져와 `processing`으로 표시. lease가 프로세스 하나만 보장하므로 안전.
2. `group_by_session(jobs)`: `source_session_id`별로 묶고 `sequence` 순 정렬.
3. 세션 묶음을 `ThreadPoolExecutor(REMOTE_WORKERS=8)`로 병렬 처리. **같은 세션은 한 스레드에서 순서대로.**
4. `process_group`: 어떤 이벤트가 대기(`waiting_context`/`retrying`)로 끝나면 **같은 세션의 남은 이벤트를 같은 due 시각으로 `pending`에 되돌림**(시도 횟수 증가 안 함). 이전에는 각자 `sequence_gap`으로 실패하며 백오프가 따로 늘어났음.
5. MySQL: `sql.pool(size)` = DBUtils `PooledDB`(최대 8, 막히면 대기, 재사용 전 ping). 이벤트 처리 후 `close()`하면 풀로 반환.
6. 잠금: `WriterLock`이 전용 연결 하나로 `GET_LOCK('nodeverse_direct_loader', 0)`을 작업자 수명 동안 유지하고, 매 묶음마다 `IS_USED_LOCK = CONNECTION_ID()`로 확인. 다른 직접 적재 도구와의 배타는 그대로.
7. 지표 복사: 별도 스레드, `updated_at` 고수위표 이후(30초 겹침) 변경분만 `bulk_write`. 오래된 값이 새 값을 덮지 않는 원자적 조건은 그대로.

설정: `REMOTE_WORKERS`(8), `REMOTE_BATCH`(200), `REMOTE_SQL_POOL_SIZE`(0=작업자 수). 의존성 추가: `DBUtils==3.1.0`.

## 4. Spark (`spark/*.py`)

- **SparkSession은 `delta_stream.main()`에서만 만든다.** 모듈은 import 시점에 Spark 객체를 만들지 않음(Column 식은 함수로: `silver.complete()`). foreachBatch 함수는 `batch.sparkSession`을 쓴다.
- **쿼리별 감시(`supervise`)**: 8개 쿼리(bronze, silver 2, audit, gold 3, remote_runtime)를 `QuerySpec`으로 관리. 하나가 멈추면 그 쿼리만 체크포인트에서 다시 시작(백오프 2·4·8…30초). 10분 안에 `QUERY_RESTART_LIMIT`(5)번을 넘으면 앱을 끝내 Docker가 컨테이너를 다시 띄움. 이전에는 하나만 실패해도 전체가 멈췄음(PL-2).
- **MongoDB 쓰기(`sinks.py`)**: `upsert()`·`delete_missing()`은 `SINK_RETRY_ATTEMPTS`(5)번 재시도 후 실패 로그를 남기고 배치를 통과시킨다(rt_*는 다음 갱신에서 복구되고 Gold Delta는 정확). `stage_outbox()`는 재시도 후에도 실패하면 예외 → 배치 재실행(이벤트를 건너뛰지 않음). 실패 횟수는 진행 파일 `/data/metrics/streaming-progress.json`의 `sink_failures`, 재시작은 `query_restarts`.
- **Silver MERGE 조건 (`silver.merge_condition`)**:
  ```
  t.event_id = s.event_id
  AND t.event_date BETWEEN (배치 최소 날짜 - 7일) AND (배치 최대 날짜 + 1일)
  AND t.event_id BETWEEN '<배치 최소 ID>' AND '<배치 최대 ID>'   -- 두 값이 UUID 형식일 때만
  ```
  - 7일: 늦은 재전송은 `event_time`이 수신 시각으로 바뀌어 원본과 날짜가 다를 수 있다(요구사항 검토서 5절 경고). 수집기 6일 제한·Kafka 7일 보관 때문에 정상 중복의 원본은 항상 이 안에 있다. 처음 넣었던 ±1일은 이 경우를 놓칠 수 있어 바로잡았다.
  - ID 범위: UUIDv7은 시간순이라 Delta 파일 통계로 건너뛰기가 된다. 매칭되는 대상 행은 반드시 배치 ID 범위 안에 있으므로 정확성에 영향 없음. 정규식으로 UUID 형식을 확인해 SQL 문자열 주입을 막는다.
- **outbox 적재(`remote/outbox.stage`)**: 500건 단위로 기존 해시를 한 번에 조회하고 `bulk_write(UpdateOne $setOnInsert)`. 이전에는 이벤트마다 왕복 2회.

## 4-1. 멈춘 이벤트 처리: `parked` 상태 (PL-9, 2026-11-20 저녁 추가)

**이전 문제:** `waiting_context`는 기한 없이 최대 60초 간격으로 무한 재시도, `retrying`은 횟수 제한 없음, `blocked`는 보이지 않음, 끝난 행은 영원히 쌓임.

**지금:** 기한이 지나면 재시도를 멈추고 `parked`로 보관합니다. 지우지 않고, 조건이 되면 되살아납니다.

| 사유 | 기한 (설정) | parked 후 되살아나는 조건 |
|---|---|---|
| `member_mapping_required` | `REMOTE_WAIT_MEMBER_HOURS` 24시간 | 작업자가 60초마다 `game_members` 행 수·최신 등록 시각과 매핑 파일 수정 시각을 보고, 바뀌면 해당 parked 행을 자동으로 `pending`에 되돌림 |
| `sequence_gap:*` | `REMOTE_WAIT_GAP_MINUTES` 10분 | 앞 번호가 적재되면 `projection.receipt()`가 바로 다음 번호를 `pending`으로 되돌림 |
| 일시 오류 (`retrying`) | `REMOTE_MAX_RETRIES` 20회 | `python -m remote.requeue requeue --reason retry_limit` |
| 데이터 오류 (`blocked`) | 즉시 (기존과 같음) | 데이터를 고친 뒤 수동 처리. 화면에 건수 표시 |

- 대기 시작 시각은 `waiting_since`에 기록하고 parked 시각은 `parked_at`에 기록합니다. 적재에 성공하면 두 필드를 지웁니다.
- 한 세션에서 어떤 행이 parked되면 같은 세션의 뒤 행은 60초 뒤로 미뤄 대기열에 되돌립니다(`process_group`).
- **운영 명령 (`remote/requeue.py`):** `status`(상태·사유별 건수), `requeue --reason <접두어> [--player <접두어>]`, `park --reason ... [--player ...]`(시험 데이터 등 지금 바로 멈추기). 행을 지우지 않습니다.
- **상태 공개:** 작업자가 10초마다 `pipeline_sink_status`(로컬·대시보드 DB 둘 다)에 상태·사유별 건수를 기록합니다. 서버 `/staff/live`의 "분석 화면 적재 상태" 카드가 이것을 보여 줍니다.
- **정리 (PL-10):** `stored`·`quarantined` 행은 `completed_at` 기준 `REMOTE_DONE_TTL_DAYS`(30일) 뒤 TTL 인덱스로 자동 삭제됩니다. parked·blocked·대기 행은 지우지 않습니다.
- 테스트 4개 추가(회원 대기 기한, 순서 빈칸·재시도 상한, 앞 번호 도착 시 되살아남, requeue/park 명령) → 파이프라인 테스트 58개 통과.

| 시험 | 결과 |
|---|---|
| 3만 건(초당 약 170~185건) 수집 | 전부 202, p50 23ms |
| 대시보드 반영 지연 | 최대 10.1~11.1초 (15초 목표 통과) |
| 원격 적재 | 3만 건 중 2만 9천9백여 건 `stored`, `blocked` 0 |

**MERGE는 아직 빨라지지 않았습니다.** 오늘 파티션에 이전 시험의 무작위 v4 ID가 10만 건 넘게 섞여 있어 모든 파일의 ID 범위가 전체에 걸쳐 있고, 그래서 ID 범위 조건이 아무 파일도 건너뛰지 못합니다. 시간이 커진 것은 같은 날 파티션 행 수가 늘었기 때문입니다(하루 안에서는 BN-1 구조 그대로). v7 효과는 **v4 데이터가 없는 새 레이크**나 v7만 쌓인 다음 날 파티션에서 다시 재야 합니다. 그 전까지 이 조건은 "손해 없이 켜 둔 상태"입니다.

## 6. 지켜야 할 규칙 (AI 에이전트용)

1. **환경 변수는 `common/settings.py`에만 추가**하고 코드는 `settings.get().<필드>`로 읽습니다. `os.getenv`를 새로 흩뿌리지 않습니다(예외: 수집 키 검사는 요청마다 `os.getenv("INGEST_KEY")`, 테스트가 import 전에 설정).
2. MongoDB 클라이언트는 `common.db.local_mongo()` / `remote_mongo()`만 씁니다.
3. Spark 모듈에서 import 시점에 `F.col(...)` 같은 Column이나 SparkSession을 만들지 않습니다(전에 이것 때문에 앱이 시작되지 않았음). `audit_state.py`는 Spark Python 워커가 import하므로 프로젝트 모듈을 import하지 않습니다.
4. 새 Spark 모듈을 추가하면 `build_compose.py`의 `SPARK_MODULES`에 넣고 `python build_compose.py`로 `compose.json`을 다시 만듭니다.
5. 새 스트리밍 쿼리는 `delta_stream.query_specs()`에 `QuerySpec(이름, FAIR 풀, 시작 함수)`로 등록합니다. 시작 함수는 `spark`를 인자로 받습니다.
6. rt_* 문서 `_id`는 `timeutil.window_key()` 형식(`ST03:2026-11-20T08:00:00Z`)을 유지합니다. 바꾸면 서버 화면이 기존 문서와 새 문서를 따로 봅니다.
7. 원격 작업자에서 같은 세션의 이벤트를 다른 스레드로 나누지 않습니다(순서 보장이 깨짐).
8. 시험 데이터는 `tools/dummy_data.py`로 만듭니다. 문제마다 `run_id`를 새로 쓰고(대시보드가 run_id를 문제 실행 키로 씀) 이벤트 ID는 v7입니다.

## 8. 남은 과제

- 끝까지 적재(초당 60~90건)가 유입(150~185건)보다 느림 → 투영(`projection.py`)의 이벤트당 Mongo 왕복(약 10회) 축소, 세션 단위 캐시.
- Silver MERGE: 새 레이크에서 v7 효과 측정. 효과가 부족하면 D19(append) 복귀 또는 하루 단위 정리(OPTIMIZE ZORDER BY event_id) 검토.
- Spark 처리 로직 단위 테스트(RF-9), 시험 스크립트 정리(RF-10, 기존 보고서가 경로를 참조해 보류).
- DLQ·격리 건수를 서버 화면에 노출(PL-8). outbox 상태 표시는 4-1에서 완료(PL-9, SV-1).
