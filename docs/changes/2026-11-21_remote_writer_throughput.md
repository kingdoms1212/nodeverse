# 8차 보완: 원격 적재 처리량 (2026-11-21)

목표는 원격 적재(outbox → 분석 화면 DB)가 유입 속도를 따라가게 하는 것입니다. 세션 안 순서, 충돌 검사(같은 ID·다른 내용은 덮어쓰지 않음), 선점 토큰, 대기 기한 같은 기존 규칙은 그대로 둡니다.

## 1. 원인

| 원인 | 확인 방법 | 내용 |
|---|---|---|
| 이벤트당 DB 왕복이 많음 | 메모리 DB로 호출 수 계측 | Mongo 약 22회 + MySQL 4회(풀 핑, 회원 조회 `FOR UPDATE`, 커밋, 반납 시 롤백) |
| 세션의 뒤 순번이 앞 순번보다 먼저 선점됨 | 9,000건 비우기 시험의 시도 횟수 분포 | 44%의 행이 한 번 이상 재시도. Silver가 한 배치를 500건씩 나눠 적재하면서 묶음마다 다른 시각을 넣어, 같은 세션의 3번이 2번보다 앞에 정렬됨 → 3번이 먼저 선점돼 `sequence_gap` 대기 |
| 대기 뒤 회복이 느림 | 코드 | 앞 순번이 저장되면 바로 다음 1건만 깨움. 같은 묶음의 나머지는 5초부터 늘어나는 대기 시각으로 남아, 세션이 백오프 간격마다 한 건씩 진행 |

## 2. 바꾼 것

| 파일 | 변경 |
|---|---|
| `remote/projection.py` | `ensure()`가 먼저 삽입하고 이미 있을 때만 읽어 비교 (새 문서는 왕복 1회) |
| `remote/projection.py` | 회원 확인 캐시: 존재하고 live인 회원만 캐시(`REMOTE_MEMBER_CACHE_SECONDS`, 기본 300초, 0이면 끔). 매핑 없음·live 아님은 매번 다시 확인 |
| `remote/projection.py` | 세션 묶음 캐시: 한 배치에서 한 스레드가 순서대로 처리하는 세션의 커서·run 컨텍스트·run·attempt 문서를 다시 읽지 않음. DB가 확인한 상태만 저장 |
| `remote/projection.py` | 다음 순번 깨우기: 한 번 확인한 뒤, 그 세션의 뒤 순번 중 순번 대기(waiting_context)와 같은 묶음에서 되돌려진 pending 행을 함께 깨움 |
| `remote/worker.py` | MySQL 연결을 실제로 쓸 때만 가져옴(캐시 적중 시 MySQL 0회). outbox 쓰기는 행마다 1회(archive 표시를 최종 상태와 함께). 대기 경로의 원격 조회 제거. 순번 대기 백오프 1초부터(다른 대기는 5초부터) |
| `remote/worker.py` | outbox 인덱스 `(source_session_id, sequence)` 추가 |
| `remote/outbox.py` | Silver 한 배치의 행은 같은 `queued_at`·`next_attempt_at`으로 적재 → 선점 정렬이 순번 순서로 됨 |

이벤트당 왕복: Mongo 약 22회 + MySQL 4회 → Mongo 약 10회 + MySQL 0회(회원 캐시 적중 시). 메모리 DB 계측 기준입니다.

## 3. 측정 (로컬 PC, 같은 스택)

**작업자만의 처리 속도:** 작업자를 멈춘 채 9,000건을 outbox에 쌓아 두고, 작업자를 켜서 비우는 데 걸린 시간을 쟀습니다.

| 버전 | 비우는 시간 | 처리 속도 |
|---|---|---|
| 변경 전 (HEAD 이미지) | 259.0초 | 34.7건/초 |
| 왕복 줄이기 후 | 168.6초 | 53.4건/초 |
| + 대기 행 함께 깨우기, 순번 대기 1초 | 67.0초 | 134.4건/초 |
| + Silver 배치 적재 시각 통일 | 41.1초 | **219.2건/초** |

참고: 왕복 줄이기만 한 상태에서 스레드를 늘리면 16스레드 81건/초, 32스레드 89건/초로 늘다가 멈췄습니다. 병목은 스레드 수가 아니라 재시도였습니다.

**같은 부하(12,000건, 초당 200건 전송) 실시간 적재**

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 적재 속도 | 57.0건/초 | 193.6건/초 (유입과 같은 속도로 따라감) |
| 전송 시작부터 다 끝날 때까지 | 224초 | 약 70초 (전송 60초 + 수 초) |
| 큐 대기 → 완료 평균 | 48.8초 | 2.9초 |
| 최종 상태 | 12,007건 stored | 12,008건 stored |

**시도 횟수 분포 (9,000건 비우기):** 왕복만 줄였을 때 1회에 끝난 행 56%(44%가 재시도) → 모두 적용 후 1회 75%. 남은 재시도는 1초 백오프라 비용이 작습니다.

## 4. 중복 제거 상태 TTL (7일) 축소 검토

별도 시험 경로(`/data/ttl-test`, 시험 후 삭제)에서 Silver와 같은 구조(`kafka_ts` 워터마크 + `dropDuplicatesWithinWatermark`, RocksDB 상태 저장소)로 시험했습니다.

| 단계 | 결과 |
|---|---|
| 168시간으로 시작 | 100행 처리 |
| 같은 체크포인트에서 48시간으로 줄여 재시작 | 오류 없이 재시작, 이미 본 ID 50건은 걸러지고 새 ID 50건만 통과 |
| 60시간 뒤 시각의 입력 | 새 ID 10건 통과. 기존 키는 168시간 시절의 만료를 그대로 유지 |
| 출력 | 160행, 고유 160 |

결론: 기존 체크포인트에서 TTL을 줄여도 안전합니다. 7일 안의 중복은 Silver MERGE 날짜 범위가, outbox 중복은 `$setOnInsert`가 막습니다. 다만 같은 TTL을 쓰는 감사 쿼리(같은 ID·다른 본문 판정)의 감지 기간도 함께 줄어듭니다. 지금 규모(키 약 23만 개)에서는 이득이 없어서 기본값 168시간은 유지합니다. 하루 이벤트가 수백만 건으로 늘면 `DEDUP_TTL_HOURS=48`로 바꾸면 됩니다.

## 5. 조정 가능한 값

| 설정 | 기본 | 용도 |
|---|---|---|
| `REMOTE_WORKERS` | 8 | 세션 그룹을 동시에 처리하는 스레드 수. 원격 DB 부하를 줄이려면 낮춤 |
| `REMOTE_BATCH` | 200 | 한 번에 선점하는 outbox 행 수 |
| `REMOTE_MEMBER_CACHE_SECONDS` | 300 | 회원 확인 캐시 시간. 회원 정보가 자주 바뀌면 줄이고, 0이면 매번 MySQL 확인 |
| `DEDUP_TTL_HOURS` | 168 | Silver 중복 제거 상태 보관 시간. 대량 수집 때 48 |

## 6. 테스트

파이프라인 81개 통과(1개 건너뜀). 추가하거나 바꾼 테스트는 다음과 같습니다.
- 세션 묶음 캐시 결과가 캐시 없이 처리한 결과와 같은지
- 회원 캐시(매핑 없음은 캐시하지 않음)
- 앞 순번 저장 시 같은 세션의 뒤 대기 행만 깨우는지(다른 세션·순번 대기가 아닌 행은 그대로)
