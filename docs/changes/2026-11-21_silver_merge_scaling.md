# 6차 보완: 데이터 증가 시 Silver MERGE 성능 검토와 압축 방식 변경 (2026-11-21)

요청: 데이터가 늘면 Silver MERGE가 느려질 가능성을 검토. 프로젝트 맥락이 없는 서브에이전트에게 독립 검토를 맡긴 뒤, 그 결과를 직접 다시 확인하고 필요한 부분만 고쳤습니다. 함께 검토한 ZORDER 비교(event_id 단독 ZORDER)는 코드를 바꾸지 않고 결론만 아래 4절에 남깁니다.

## 1. 검토 결과 요약

| 위험 | 서브에이전트 판단 | 직접 확인 | 조치 |
|---|---|---|---|
| A. Delta 자동 압축이 거의 매 커밋마다 날짜 파티션 전체를 다시 씀 | 높음 | **사실.** 최근 Silver 커밋 40개 중 MERGE 20, 자동 OPTIMIZE 20. 매번 파일 2개(약 30MB) → 1개. 실데이터 약 30MB인 Silver가 디스크 4.9GB(파일 658개), Bronze 7.5GB. `autoCompact.minNumFiles=100`이 사실상 적용되지 않음 | **수정 (아래 2절)** |
| B. 중복 제거 상태(7일) 정리 비용이 키 수에 비례 | 높음 (지속 고부하 시) | 서브에이전트 별도 경로 실험: 키 135만 → 0.74초, 1,890만 → 11.5초(태스크 합계). 현재 키 약 23만이라 지금은 영향 작음 | 기록만 (5절 권고) |
| C. 배치에 v4 ID나 며칠 늦게 처음 도착한 v7 ID가 섞이면 ID 범위 조건이 넓어짐 | 중간 (조건부) | 코드상 사실. 같은 이벤트의 재전송은 상태 저장소가 먼저 거르므로 해당 없음. 오프라인 큐·서버 장애 복구 직후에만 발생 | 기록만 (5절 권고) |
| D. 트랜잭션 로그·체크포인트 증가 | 중간 | 자동 압축 때문에 배치당 커밋이 2개였음 | A 수정으로 배치당 1개 |
| E. 같은 4코어 경쟁 (주기 작업, 압축) | 낮음~중간 | A의 매 배치 압축이 가장 큰 몫 | A 수정으로 완화 |

날짜 조건([배치 날짜 −7일, +1일]) 덕분에 전체 이력이 늘어나는 것 자체로는 MERGE 조인 범위가 커지지 않는다는 점은 두 검토가 같았습니다.

## 2. 바꾼 것

| 파일 | 내용 |
|---|---|
| `spark/tables.py` | `autoCompact.enabled=false`. `optimize.minFileSize=64MB`, `optimize.maxFileSize=128MB` (64MB에 이른 파일은 다시 쓰지 않음) |
| `spark/compaction.py` (신규) | `compact_after_write()`: 테이블의 유일한 쓰기 스레드가 자기 쓰기 직후, `COMPACT_EVERY_BATCHES`(기본 300)배치마다 건드린 파티션만 OPTIMIZE. 같은 스레드라 그 MERGE와 충돌할 수 없음. `compact_append_only()`: Bronze(append만)를 주기 스레드에서 10분마다 오늘·어제 ingest_date 압축. `vacuum()`: `VACUUM_INTERVAL_HOURS`(6)마다 모든 Delta 테이블 VACUUM, 보존 `VACUUM_RETAIN_HOURS`(168 = Delta 기본) |
| `spark/silver.py` | MERGE 뒤 `compact_after_write(table, "event_date", {lo, hi})` |
| `spark/gold.py` | Gold MERGE 뒤 `compact_after_write(table)` |
| `spark/periodic.py` | Bronze 압축 10분, VACUUM 6시간 (시작 약 10분 뒤 첫 실행) |
| `common/settings.py`, `build_compose.py`, `compose.json` | 위 설정 4개, `compaction.py`를 `--py-files`에 추가, `COMPACT_EVERY_BATCHES` 전달 |

OPTIMIZE는 `dataChange=false`로 커밋되므로 Silver→Gold, Bronze→Silver 스트림은 다시 읽지 않습니다(5차 시험에서 확인한 동작).

## 3. 확인 결과 (같은 부하: 6,000건, 초당 100건, 592세션)

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| Silver learning 배치 중앙값 / p95 | 5.65초 / 6.90초 (12배치) | 1.75초 / 4.20초 (22배치) |
| 그중 MERGE 단계 중앙값 | 5.35초 | 1.55초 |
| 시험 1회 동안 늘어난 디스크 (Silver / Bronze) | +420MB / +633MB | +2MB / +2MB |
| 최근 Silver 커밋 구성 | MERGE 1 : 자동 OPTIMIZE 1 | MERGE만 (압축은 300배치마다) |
| gold_1m 배치 중앙값 | 3.60초 | 2.20초 |
| 원격 적재 완료 (전송 시작부터) | 104초 | 81초 |
| 대시보드 지연 (15초 기준) | 통과 | 통과 |
| sink 실패 · 쿼리 재시작 | 0 · 0 | 0 · 0 |

압축이 실제로 도는 경우는 `COMPACT_EVERY_BATCHES=5`로 띄워 부하 중에 확인했습니다. Silver 22개 → 1개(4.3초), gold_1m 9 → 1, gold_alert 4 → 1. 충돌 예외, 쿼리 재시작, sink 실패는 없었습니다. 확인 뒤 기본값 300으로 되돌렸습니다. Bronze 10분 압축과 VACUUM 실행 결과는 3-2절에 적습니다.

### 3-2. Bronze 주기 압축과 VACUUM 실행

| 작업 | 결과 |
|---|---|
| Bronze 압축 (재기동 10분 뒤) | 오늘·어제 ingest_date: 124개 파일 → 1개, 2.5초 |
| VACUUM (재기동 10분 뒤, 이후 6시간마다) | 테이블당 9~12.5초, 전체 약 80초. sink 실패·쿼리 재시작 0 |

처음에는 VACUUM이 주기 스레드 안에서 돌아, 그 약 80초 동안 rt_summary 갱신이 멈췄습니다(실시간 화면의 "수집 지연" 기준 30초를 넘김). 그래서 VACUUM을 별도 스레드(`vacuum_safely`)로 옮겼습니다. 옮긴 뒤 VACUUM 중에도 rt_summary가 10초마다 갱신되는지 확인했습니다(아래 3-3).

### 3-3. VACUUM 별도 스레드 확인

재기동 10분 뒤 23:59:40~00:01:09에 VACUUM 8개 테이블이 돌았습니다(테이블당 8.9~14.5초). 같은 시간 동안 rt_summary는 00:00:00, 00:14, 00:25, 00:35, 00:45, 00:56, 01:06으로 약 10초마다 계속 갱신됐습니다(소요 0.3~1.05초). 실시간 화면의 수집 지연 기준 30초를 넘기지 않았습니다.

### 3-1. 이미 쌓인 디스크

이전 사본(Silver 4.9GB, Bronze 7.5GB)은 대부분 오늘 만들어져 보존 기간 7일이 지나야 VACUUM으로 지워집니다. 바로 비워야 하면 스트림을 멈추고 `spark.databricks.delta.retentionDurationCheck.enabled=false`로 짧은 보존 VACUUM을 한 번 실행할 수 있지만, 늦게 도는 스트림이 지운 파일을 찾을 수 있어 운영 판단이 필요합니다. 디스크 여유는 921GB입니다.

## 4. event_id 단독 ZORDER 비교 (코드 변경 없음)

`pipeline/docs/SILVER_MERGE_ZORDER_REQUEST_2026-11-21.md` 요청을 별도 시험 경로(93만 행, 4일, 날짜당 7파일)에서 비교했습니다. 결론은 **현행 `ZORDER BY (minigame_id, player_id, event_id)` 유지**입니다.

| 데이터·배치 | MERGE 대상 스캔 A(현행) | B(event_id) | MERGE 중앙값 A / B |
|---|---|---|---|
| v4·v7 혼합, 신규 3,000건 | 20파일 97MB | 4파일 22MB | 1.16 / 1.08초 |
| 혼합, 신규 + 날짜 넘긴 재전송 1,000건 | 28파일 140MB | 28파일 152MB | 1.77 / 1.68초 |
| v7, 신규 | 0파일 | 0파일 | 1.24 / 1.25초 |
| v7, 신규 + 재전송 | 28파일 119MB | 28파일 116MB | 1.86 / 1.83초 |

B는 v4가 섞인 날짜의 신규 배치에서만 스캔을 줄였습니다. MERGE 범위가 7일이라, v4 데이터가 빠지면 그 이득도 사라집니다. 반면 플레이어 1명 조회는 B에서 2.4~2.6배 더 읽었습니다. 정비 전후 행 수·고유 ID, 재전송 1건·원래 날짜·본문 유지, 정비 뒤 체크포인트 스트림 재개(다시 읽은 행 0)는 A·B 모두 정상이었습니다.

## 5. 남긴 권고 (이번에 바꾸지 않음)

1. **중복 제거 상태 TTL (위험 B):** `DEDUP_TTL_HOURS`를 168에서 24~48로 줄이면 상태 정리 비용이 비례해서 줍니다. 7일 안의 중복은 MERGE 날짜 범위가 막아 주므로 Silver 정합성은 유지됩니다. 다만 기존 체크포인트와의 호환과, MERGE까지 오는 재전송이 늘어나는 영향을 시험해야 해서 이번에는 바꾸지 않았습니다. RocksDB `changelogCheckpointing`도 함께 시험할 항목입니다. 하루 이벤트가 수백만 건 수준으로 늘기 전에 진행하면 됩니다.
2. **MERGE 입력 분리 (위험 C):** v7 ID 안의 생성 시각으로 이상치(v4, 며칠 지난 v7)를 따로 묶어 MERGE하면 ID 범위가 넓어지지 않습니다. 오프라인 큐·장애 복구 직후에만 생기는 경우라 우선순위가 낮습니다.
3. **트리거 간격:** Silver 1초 트리거는 대시보드 지연(15초 기준) 때문에 유지합니다. 압축을 배치에서 떼어 내 배치당 커밋이 1개가 됐습니다.
4. **디스크 감시:** VACUUM 주기와 별개로 lake 볼륨 사용량을 운영 지표로 보는 것을 권합니다.
